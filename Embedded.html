DRS · for embedded developers · beta

A free control panel for every board you build

DRS draws the panel for your ESP32, Arduino, Atmel (AVR), PIC, Raspberry Pi, Raspberry Pi Pico, Radxa or LattePanda project, and then stores, prints and passes on what the board reports. Test benches, parameter screens, home automation and data logging all use the same tool, and it costs nothing.

This is a beta release. It is still being tested, so something may not work as you expect. Tell us what you find.

Connect

Any board, four ways to talk

Pick what your board already speaks. A board does not need a special chip: if it can send and receive bytes, it can have a panel.

LZ protocol

One tag in each request, one answer back, over a serial port, TCP or Bluetooth. It is written for the Arduino way of programming, so it fits every microcontroller.

MQTT

DRS has its own broker and also connects to the one you already run. Topics become values on the panel and back.

REST over HTTP

The board posts its readings to DRS with a plain HTTP request. Nothing to install on the board.

Modbus

A board or a PLC that already speaks Modbus needs no LZ at all.

How it works

DRS writes the Arduino sketch for you

You do not write a protocol or a user-interface program. Draw the panel, and DRS generates the board side from the same tags.

Draw the panel

Add an LZ client and its tags: Led, Button, Analog. Link a switch, a button and a dial to them.

Generate the sketch

Choose Generate Arduino Server on the client. DRS writes the .ino file that answers those tags, for a serial port, Ethernet, WiFi or Bluetooth.

Upload it

Open the file in the Arduino IDE and upload it to the board. Add your own code in the loop.

Run

The panel reads the button and the analog value and writes the LED. Change a tag in the panel and the board follows.

No board yet?

Run the same sketch in drQEmu and test the panel against the emulated ESP32.

The protocol is plain text, so any chip can speak it

One line per tag, ended with a carriage return. A request with no value is a read; a request with a value is a write. You can try it by hand in any serial terminal.

panel asks   Led:<CR>      board answers   Led:0<CR>
panel writes Led:1<CR>      (the board sets the pin; no answer)

That is why it is not tied to one family. The generated sketch is a short tag table and a line scanner. A PIC, an AVR, a Raspberry Pi Pico or a board in any other language needs only the same few lines on its serial port or socket. This is the heart of the sketch DRS generates for the three tags above:

Tags[0] = (TTags) {"Led",0};
Tags[1] = (TTags) {"Button",0};
Tags[2] = (TTags) {"Analog",0};

void loop() {
  if (Tags[0].TagValue == 1) digitalWrite(PIN_LEDTAG, HIGH); else digitalWrite(PIN_LEDTAG, LOW);
  Tags[1].TagValue = (int)digitalRead(PIN_BUTTONTAG);
  Tags[2].TagValue = (int)analogRead(PIN_ANALOGTAG);
  ScanLZPacked();      // answers the panel's requests
  delay(10);
}

Try it in ten minutes

A working pair: a panel and the sketch DRS generated for it. A switch drives the LED, a button and an analog input come back. Open the sketch in the Arduino IDE and upload it to an ESP32 (the pins are 2, 0 and 34; change them for your board), then open the panel in DRS and set its serial port to the one your board uses. Without a board, run the sketch in drQEmu.

The panel

Gateway

Put DRS between your devices and the outside

Zigbee coordinators and your own boards already speak MQTT. Connect them straight to the DRS MQTT server, and open the data to the web and to other systems from the same place, as a gateway you set up in minutes instead of a separate service to deploy.

MQTT to REST and the web

What a Zigbee coordinator or a board publishes to the MQTT server is also offered as REST endpoints and web pages, so a browser, an app or an ERP can read it without speaking MQTT. A web request can publish back to a topic.

Test over HTTP

Test a board that sits on a serial port from a browser or a script over plain HTTP: DRS takes the request, asks the board on the serial port and returns the answer.

Any port to any port

Open a project, drop a serial port and a TCP connection and link them: the bridge is ready, and a board on a serial port is reachable over the network. Every protocol runs full duplex, so data flows both ways at once. Serial, TCP, UDP, HTTP, MQTT, Bluetooth and Modbus can be joined in any combination, and one input can feed many outputs at once. Read a serial port once and send what arrives to an MQTT topic, an HTTP service, a TCP peer, a database and a file together, and the other way round.

Your rules in the middle

Your own blocks and scripts decide what is forwarded, converted or answered, and the user manager guards who may reach it.

Your own code

Write the parts only you know

A frame decoder for your board, a sensor conversion, calibration maths: write them in your own compiled library. DRS brings its functions into blocks and scripts, so the panel calls them like built-in ones.
